# Architecture

Type Evidence combines an exact-identity font catalog, a local discovery engine, a renderer and model-neutral CLI/MCP interfaces. Its optional visual component searches rendered letterforms through FontCLIP. Its composition component makes selections inspectable together in the intended hierarchy and content.

## From sources to a design decision

1. **Pinned acquisition.** The source lock records full Git commits. Full collections use clean Git checkouts or portable blob materialization; selected upstream directories use a bounded file manifest with byte lengths, Git blob hashes and SHA-256. The current lock preserves both original collections and adds selected Google Fonts and Arrow Type material. `pin-source` makes further additions reproducible without cloning an entire large repository.
2. **Preparation.** Recognized Base64 containers and bounded ZIP/7z members produce separate content-addressed derivatives. Originals remain intact. A manifest records container/member hashes and transformations. No upstream programs or nested archives are executed. Unsupported material stays visible in preparation/index reports.
3. **Inspection.** Signatures determine format. fontTools reads collection faces, cmap coverage, names, styles, axes, features, versions and legal notices. Sample outline bounds and advances are measured. FreeType must load and rasterize a sample. Failures remain in the issue ledger.
4. **Identity and families.** `sha256:face_index` identifies an exact source face. Byte copies retain all origins. A separate decoded-table hash identifies some equivalent containers without replacing their source identities. Family/vendor/version/width class define conservative groups. `required_styles` resolves exact companion faces and axes that cover the same text; observed style counts do not establish a complete family.
5. **Visual indexing.** FontCLIP embeds an actual rendered sample from each eligible face at its default axes. Indexing starts with family representatives, then visits remaining faces. It commits in batches and can resume. Canonical table-equivalent containers can reuse an embedding while retaining exact-ID provenance. No popularity, license-status or known-category filter controls index membership. Unsupported samples become explicit failures; their fonts remain available to ordinary discovery.
6. **Discovery and exploration.** Hard text/style/family constraints precede ranking. Negation-aware aliases, literal name matches, measured context preferences and optional learned appearance evidence contribute separately labeled reasons. A bounded result page contains distinct family alternatives; pagination, explicit exclusions, visual neighbors and reference images let an agent revise its direction. An eligible existing font retains a baseline slot. Familiarity and novelty are not scoring features.
7. **Contextual rendering.** HarfBuzz shapes and FreeType rasterizes the same verified source bytes at explicit coordinates. Missing cmap characters or shaped glyph zero fail. Specimens compare common text/sizes; compositions place roles together in text, columns, panels and tables. Line breaks use actual shaped advances. Requested line heights are retained, oversized unbreakable content is rejected, and potential line-ink overlap is reported for inspection.
8. **Implementation.** Resolve verifies the selected file again. Composition recipes provide scoped CSS family aliases, real styles, axes/features and local asset URLs. Fonts are never copied automatically. The accompanying browser loader verifies SHA-256 and loads every face before revealing the layout. The agent then checks the actual target application and explains its choice.

## Local visual retrieval

The adapter uses the released [FontCLIP implementation at commit `3d4c6af`](https://github.com/yukistavailable/FontCLIP/tree/3d4c6af01f668800d8e4f9f4f753d29c74dad252) and its approximately 653 MB checkpoint, pinned by SHA-256. `visual-setup` is the only model-download command. Loading uses PyTorch's restricted weights-only loader, folds the released text LoRA into the corresponding CLIP weights, and requires a strict state match. [CPU float32 parity evidence](../evidence/v0.2/fontclip-parity.json) compares text/image embeddings and attention projections against the pinned official implementation. It also records sampled cross-container render equality; neither check proves aesthetic quality.

The visual index stores 512-dimensional vectors and sample evidence: exact source digest, script/text, shaping language, default axes, rendered-mask digest and model-associated attributes. The default index uses the first complete supported sample, preferring Latin. `visual-index --script SCRIPT` builds a separate index for a specific writing system and pins its sample text and language. Supported script options are documented in [agent integration](agents.md#search-the-writing-system-you-will-use). These are recorded samples, not every glyph or variable instance.

Search detects the non-Latin writing system in the actual text and selects that script's index. Han-only text uses the language tag to distinguish Japanese, Korean and Traditional Chinese from the default Chinese sample. Missing or unsupported script indexes produce explicit status/errors and metadata discovery where allowed; they never reuse Latin glyph similarity as script evidence.

At search time, positive appearance terms, negative terms, neighbor/avoidance references and an optional image crop contribute cosine similarities. Scores are standardized against the current visual corpus and combined with ordinary labeled preferences. Model associations such as “humanist” or “playful” are learned interpretations; they are not imported into the catalog as declared facts. Unindexed faces receive no visual score and remain eligible.

`visual=auto` attempts local visual retrieval when applicable and reports a fallback if it is unavailable. `visual=on` requires it; `visual=off` preserves the metadata/measurement baseline. Reference-image requests require visual retrieval. Search performs no model download or hosted inference.

[Fontmap](https://github.com/tfrere/fontmap) informed the investigation of rendered-font discovery; its application and pipeline code are not used here. [fontTools](https://fonttools.readthedocs.io/en/latest/ttLib/ttFont.html), [HarfBuzz](https://uharfbuzz.readthedocs.io/) and [FreeType](https://freetype.org/freetype2/docs/) remain the inspection/shaping/rasterization foundation. Pillow composes pixels and separate specimen-interface labels.

## Interfaces and context budget

`operations.discover` is shared by CLI search and MCP `font_search`. It selects the retrieval mode, then calls the deterministic ranker with optional visual evidence. The remaining operations expose exact metadata, resolution, family inventory, bounded project hints, specimens, compositions, issues and status.

MCP sends compact summaries and one inline preview image by default. Glyph-by-glyph geometry, complete manifests and application recipes remain on disk. Agents can page results or reopen a generated PNG without reading the catalog into context. Setup and acquisition stay explicit CLI operations rather than tool calls that unexpectedly download gigabytes.

## Limits that change decisions

- **Fit still needs judgment.** Learned resemblance and measured proportions make exploration more useful; neither certifies audience fit, readability, accessibility or a good pairing. Context fields have documented, bounded effects. The language tag helps select a Han-script sample and guides rendering; surroundings remain handoff context for the agent's inspection.
- **Metadata and coverage are imperfect.** Names, PANOSE, weights and family grouping can be wrong. Hard category filters exclude unknown categories by design; descriptive visual search does not. Cmap presence is only the first text check; actual shaping is verified when rendering.
- **Samples have a scope.** Catalog metrics use a documented Latin sample at default coordinates. Visual vectors use one supported script sample at default axes. A reference image may carry layout/decoration cues beyond the font. Render the requested text and nondefault settings before choosing.
- **Rendering is a preview.** Unhinted grayscale outlines with 4× supersampling differ from browser/OS hinting and final printers or game engines. Same-direction LTR scripts and simple RTL runs are supported; mixed-direction paragraphs, mixed-script RTL, variation selectors, color/bitmap fonts and vertical layout are rejected. Wrapping uses whitespace rather than language-specific hyphenation or full Unicode line breaking.
- **Recipes are exact but not automatic deployment.** They require authorized asset staging and target-environment inspection. Collection members need a deliberate standalone derivative for browser use. Print-preview dimensions are pixels, without physical-size or color-profile guarantees.
- **Coverage is reported, not inferred.** Source preparation, catalog inspection and visual indexing each have their own counts and failures. A stored vector count alone does not establish complete current-catalog coverage. Use versioned reports and `visual-status`.
- **Platform claims are scoped.** The runtime, source paths and browser font gate have macOS evidence. Native Windows end-to-end use and visual acceleration on other hardware are not established by those checks.
- **Outcome evaluation is separate.** Unit tests and upstream model parity validate behavior. The historical v0.1 evaluation predates visual retrieval and contextual composition; it does not establish improved v0.2 design outcomes. Consult versioned evaluation evidence as it is added.

Font parsers operate locally, not inside a hostile-file security sandbox. Font rights remain independent of ranking, and model weights/fonts are excluded from source and review archives. Maintenance and source-preservation details are in [maintenance](maintenance.md).
